## 1. React version reality in 2026

- **Current stable React is 19.3** (blog 2026-09-09; `v19.3.0`). Prior: 19.2 (2025-10-01), 19.1 (2025-03-28), 19.0 (2024-12-05). **React publishes no LTS.** https://react.dev/versions
- **19.3 stabilised `<ViewTransition>` and Fragment Refs**, added `addTransitionType`, `browser()` / `use(browser())` to opt a component out of SSR, and Trusted Types integration (React no longer coerces values to strings before DOM sinks). https://react.dev/blog/2026/09/09/react-19-3
- **19.2 added `<Activity>`** (`mode="visible" | "hidden"`; hidden unmounts effects, defers updates, preserves state for back-navigation) and **`useEffectEvent`**. https://react.dev/blog/2025/10/01/react-19-2
- **React Compiler is stable (v1.0)** — a build-time tool whose docs say it works by "eliminating the need for manual `useMemo`, `useCallback`, and `React.memo`". https://react.dev/learn/react-compiler
  - Memoizes more precisely than a human, including after an early return, where `useMemo` cannot be used.
  - `useMemo`/`useCallback` remain an escape hatch (notably to keep an Effect dependency stable). For existing code: leave memoization in place, or test carefully before removing — removal changes compiler output. https://react.dev/blog/2025/10/07/react-compiler-1
  - Backwards compatible to React 17 via `react-compiler-runtime` + a `target` config. On Vite it installs as a Babel plugin through `vite-plugin-react`. Compiler-powered lint rules ship in `eslint-plugin-react-hooks`'s `recommended` preset and need no compiler installed.
  - If you lack e2e coverage, **pin it exactly** (`--save-exact`), not a SemVer range — changed memoization can change how an Effect fires.
- **`use`, `useOptimistic`, `useActionState`, `useTransition` are stable.** I grepped each reference page for `Experimental`/`Canary`/`unstable`: zero matches — and the docs *do* use an explicit badge elsewhere (e.g. `<Suspense defer>`), so the convention exists and these sit outside it. https://react.dev/reference/react/use · /useOptimistic · /useActionState · /useTransition
- **`useEffectEvent` shipped in 19.2 and is stable** (no experimental badge). https://react.dev/reference/react/useEffectEvent
- Limitations that are **not** instability: state updates after an `await` inside an Action need a nested `startTransition`; Transitions cannot control text inputs; `useActionState` batches concurrent Actions. https://react.dev/reference/react/useTransition

## 2. Data fetching

- React frames fetching as *synchronization*, not an event. Fetching in an Effect is permitted, with four documented downsides: "Effects don't run on the server"; "makes it easy to create 'network waterfalls'"; "you don't preload or cache data … if the component unmounts and then mounts again, it would have to fetch the data again"; "It's not very ergonomic." https://react.dev/learn/synchronizing-with-effects#what-are-good-alternatives-to-data-fetching-in-effects
- Cleanup is mandatory: "If your Effect fetches something, the cleanup function should either abort the fetch or ignore its result" — else an out-of-order response paints stale data. https://react.dev/learn/you-might-not-need-an-effect
- **React names libraries**, verbatim: "If you use a framework, use its built-in data fetching mechanism." "Otherwise, consider using or building a client-side cache. Popular open source solutions include **TanStack Query**, **useSWR**, and **React Router 6.4+**." https://react.dev/learn/synchronizing-with-effects
- **`use` + Suspense outside a framework is supported, but you own the cache**: "you can read a Promise with `use` directly, as long as the Promise is cached so the same instance is reused across renders." Caveats: no try/catch, and `fetch` "creates a new Promise on every render". https://react.dev/reference/react/Suspense#suspense-enabled-frameworks · https://react.dev/reference/react/use
- **Suspense does not detect Effect-based fetching**: "It only activates in the cases listed below." https://react.dev/reference/react/Suspense
- **TanStack Query documented defaults**: `staleTime` effectively **0**; stale queries refetch on mount, window refocus, and reconnect; failures retry **3× with exponential backoff**; inactive queries GC after **5 min**; **structural sharing on by default**, and it "only works with JSON-compatible values". https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults
- TanStack's optimistic pattern: `onMutate` (cancel → snapshot → `setQueryData` → return snapshot) / `onError` (restore) / `onSettled` (`invalidateQueries`). https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates
- **Is it warranted?** The docs' own criteria are the four gaps above. **[opinion]** The deciding question is not "cache or not" but *who owns invalidation*. One polled list plus a WS ping is served by a small deduped fetch layer; adopt TanStack Query at the second independently invalidated resource — or immediately, if its structural sharing is what stops a 5 s poll from re-rendering unchanged rows.

## 3. Effect discipline

- "You Might Not Need an Effect" names two cases where an Effect is **wrong**: transforming data for rendering, and handling user events. "You *do* need Effects to synchronize with external systems." https://react.dev/learn/you-might-not-need-an-effect
- The rules as written: calculate during render; don't mirror props/state into state; `useMemo` only after measuring (docs suggest ~1 ms+); reset a subtree with a **`key`**, not an Effect that clears state; adjust partial state *during render* (`if (items !== prevItems) { setPrevItems(items); … }`); put event-caused logic in event handlers; lift state up instead of syncing components via Effects; never chain Effects that each set state for the next.
- **"Code that runs because a component was *displayed* should be in Effects, the rest should be in events."** Same page.
- One-time app init must not be an Effect (Strict Mode runs it twice): use a module-level `didInit` flag or top-level module code in the entry module. https://react.dev/learn/you-might-not-need-an-effect#initializing-the-application
- **External-store subscriptions belong in `useSyncExternalStore`**, not `useEffect` + `useState` — the docs call the Effect version "Not ideal" and the hook "less error-prone". Snapshots must be immutable; repeated `getSnapshot` calls must return the same value until the store changes. https://react.dev/reference/react/useSyncExternalStore
- **The three shapes Kohlab actually has, each with a documented `useEffectEvent` recipe** (https://react.dev/reference/react/useEffectEvent):
  - **Interval** — `setInterval` in an Effect with `[]` deps; read latest values through an Effect Event. Verbatim: "`onTick` Effect Event reads the latest `count` and `increment` without causing the interval to restart."
  - **Event listener** — register once in an Effect with `[]`; "the event listener is only set up once when the component mounts" because the callback is an Effect Event.
  - **WebSocket / external system** — same shape: the Effect owns connect + cleanup, Effect Events own message handling, so app settings never reconnect the socket.
- **Hard constraints on `useEffectEvent`** (docs' Pitfalls): must **not** appear in a dependency array; callable only from Effects or other Effect Events, never during render or passed to child components; identity intentionally changes every render; "Do not use `useEffectEvent` to avoid specifying dependencies." It is not a lint suppressor.
- Strict Mode double-invokes Effects in dev, so every subscription needs symmetric cleanup. https://react.dev/learn/synchronizing-with-effects
- `useSyncExternalStore` caveat for a WS-fed store: if the store mutates during a non-blocking Transition, React re-checks the snapshot before committing and **falls back to a blocking update** to keep the screen consistent. Do not suspend on a store value. https://react.dev/reference/react/useSyncExternalStore

## 4. Optimistic UI

- `const [optimisticState, setOptimistic] = useOptimistic(value, reducer?)`. https://react.dev/reference/react/useOptimistic
- **The setter must be called inside an Action** (`startTransition(...)`, or an `action` prop, which is already inside a transition). Outside one it warns and the optimistic value "briefly renders" then snaps back — "there's no Transition to 'hold' the optimistic state while your Action runs."
- **There is no manual rollback API, and none is needed.** Verbatim: "There's no extra render to 'clear' the optimistic state. The optimistic and real state converge in the same render when the Transition completes." On failure, "the parent typically only updates `value` on success, so … the UI shows what it showed before the optimistic update. You can catch the error to show a message."
- **The reducer form is the realtime-merge primitive**: "If `items` changes while the Action is pending, React re-runs your `reducer` with the new `items` to recalculate the state. This keeps your optimistic additions on top of the latest data."
- `useActionState(reducerAction, initialState)` → `[state, dispatchAction, isPending]`. Known errors are **returned** as reducer state and rendered; unknown errors are **thrown** and "React will cancel all queued Actions and shows the nearest Error Boundary". Calls execute **sequentially**, each receiving the previous return value. https://react.dev/reference/react/useActionState

## 5. Caching and realtime merge

No spec prescribes a polling/WS merge algorithm; this is a design problem and I will not present a convention as a standard. What the primary sources actually give you:

- **The mechanism for "server snapshot wins, overlays survive"** is `useOptimistic`'s reducer recompute: when the base `value` changes mid-flight React re-runs the reducer against the new base. Documented behaviour, not a trick. https://react.dev/reference/react/useOptimistic
- **Structural sharing is TanStack Query's anti-flicker mechanism**: refetched data that is deep-equal to the cache keeps its identity, so a poll that changed nothing causes no re-render. Caveat: JSON values only. https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults
- **Keep previous data across a key change** with `placeholderData: (previousData) => previousData`; placeholder data "is not persisted to the cache" and sets `isPlaceholderData: true`. https://tanstack.com/query/latest/docs/framework/react/guides/placeholder-query-data
- **Invalidation is the atomic-update primitive**: `invalidateQueries` marks stale (overriding `staleTime`) and refetches in the background — "targeted invalidation, background-refetching and ultimately atomic updates". https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation
- **Defer non-urgent re-renders** with `startTransition` / `useDeferredValue`; Suspense will *not* re-show a fallback for a re-suspend caused by either. https://react.dev/reference/react/Suspense
- **Pause polling on hidden tabs.** MDN names this exact case: "An application showing a dashboard of information doesn't want to poll the server for updates when the page isn't visible." It also documents that **tabs with an open WebSocket are exempt from background timer throttling** while `setTimeout`/`setInterval` are throttled — so gate rendering/polling on `visibilityState`; the socket needs no special handling. https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API

## 6. Component architecture

- **Code splitting**: `lazy(() => import('./X'))` defers the *fetch* to first render; declare it **outside** components (inside, "all state [is] reset on re-renders") and as a **default export**. A rejected promise is thrown "for the nearest Error Boundary to handle". https://react.dev/reference/react/lazy
- **Suspense caveats for a dashboard**: content is revealed "at most once every 300 ms"; state is *not* preserved for a tree that suspended before first mount; a re-suspend re-shows the fallback unless the update came from `startTransition`/`useDeferredValue`; hiding visible content cleans up **layout Effects** in that tree. https://react.dev/reference/react/Suspense
- **Vite**: dynamic imports must start with `./`, `../` or `#` and end with a file extension; `import.meta.glob` is lazy and split per file; CSS for an async chunk is extracted and the chunk is only evaluated after its CSS loads (no FOUC); Vite rewrites dynamic imports with a preload step so shared chunks download in parallel. Workers use `new Worker(new URL('./w.js', import.meta.url), { type: 'module' })`. https://vite.dev/guide/features
- **Vite 8 is Rolldown-based and `build.rollupOptions` is deprecated** ("an alias of `build.rolldownOptions`"). Rolldown chunks via `output.codeSplitting.groups`, not `manualChunks`. https://vite.dev/config/build-options · https://rolldown.rs/in-depth/manual-code-splitting
- **Error boundaries**: a class component with `static getDerivedStateFromError` (+ optional `componentDidCatch`); React's docs point at `react-error-boundary` if you'd rather not hand-roll. Without one, "if your application throws an error during rendering, React will remove its UI from the screen." https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary
- **What boundaries do NOT catch** (verbatim): event handlers, server-side rendering, errors thrown in the boundary itself, and "asynchronous code (e.g. `setTimeout` or `requestAnimationFrame` callbacks); **an exception is the usage of the `startTransition` function returned by the `useTransition` Hook** — errors thrown inside the transition function are caught by error boundaries." That is the concrete React 19 async change: *Actions are the async path a boundary can catch.* https://react.dev/reference/react/Component
- **React 19 root error reporting**: `createRoot(container, { onCaughtError, onUncaughtError, onRecoverableError })`, each receiving `(error, errorInfo)` with a `componentStack`. React 19 also de-duplicated logging — a caught render error used to emit three console errors; now it emits one with the owner stack and boundary message. `captureOwnerStack` is the documented dev-time Owner Stack helper. https://react.dev/reference/react-dom/client/createRoot · https://react.dev/blog/2024/12/05/react-19
- **Where boundaries must exist** **[opinion, derived from the two facts above]**: one root boundary; one per independently-failing panel (terminal, log, diff, file tree); one around every `lazy`+`Suspense` region, since a failed chunk load throws into the nearest boundary. Everywhere else, one throw blanks the screen.

## 7. Styling architecture at scale

- **Tailwind v4 is CSS-first.** Tokens are declared in CSS with `@theme`; the docs distinguish `@theme` (a token that *also* creates utilities, e.g. `--color-mint-500` → `bg-mint-500`) from `:root` ("regular CSS variables that should not have corresponding utility classes"). `tailwind.config.js` survives only via the **Compatibility** `@config` directive; `theme()` is deprecated; `corePlugins`/`safelist`/`separator` are unsupported in v4. https://tailwindcss.com/docs/theme · https://tailwindcss.com/docs/functions-and-directives#compatibility
- **Theme variables are real CSS custom properties**, readable directly (`var(--color-mint-500)` in arbitrary values or inline styles). Tailwind leans on native CSS variables internally and positions itself as the preprocessor; Sass/Less/Stylus are unsupported by design. https://tailwindcss.com/docs/compatibility
- **The class-soup mitigation is a scanning constraint, not taste**: Tailwind "treats all of your source files as plain text, and does not attempt to actually parse your files as code in any way", so it "has no way of understanding string concatenation or interpolation". Never build class names dynamically (`bg-${color}-600`); map props to **complete static class strings**. https://tailwindcss.com/docs/detecting-classes-in-source-files
- **CSS Modules vs utilities vs custom properties**: the Tailwind docs discourage CSS Modules ("styles are naturally scoped with utilities, and each module forces a separate Tailwind pass — slower builds"); `@apply` requires `@reference` in module/Vue/Svelte files. https://tailwindcss.com/docs/styling-with-utility-classes · https://tailwindcss.com/docs/compatibility#css-modules
  - **[opinion]** Defensible split for Kohlab: utilities for layout/spacing/typography; `@theme` properties for colour/radius/spacing tokens (already true); hand-written CSS only for what utilities cannot express — xterm viewport and scrollbar styling, Monaco sizing, `content-visibility`. Use CSS Modules only to style a third-party DOM subtree.
- **Variant composition**: `class-variance-authority` gives `variants`, `compoundVariants`, `defaultVariants`, `VariantProps<typeof x>`; it emits no CSS and is 580 B compressed. Its own docs defer conflict resolution to tailwind-merge: "for bulletproof components, wrap your cva component with `twMerge`", shipping the example `twMerge(buttonVariants(variants))`. https://cva.style/getting-started/variants · https://cva.style/getting-started/installation#handling-style-conflicts
  - cva is still **0.7.1** — 0.x, no 1.0 banner. Its docs describe a future shorter npm name that does not appear to have shipped; do not assume it exists. https://registry.npmjs.org/class-variance-authority/latest
  - cva depends on `clsx` at runtime. The cva+clsx pairing is a vendor fact; the wider `cva + clsx + tailwind-merge` stack is a **community convention** — only cva's docs mention tailwind-merge, and tailwindcss.com/radix-ui.com/base-ui.com/react-spectrum.adobe.com do not codify it. Label it as convention, not standard.
- **Primitives — what each library's own docs claim**:
  - **Radix Primitives** — unstyled, "ship without styles, giving you complete control"; handles "aria and role attributes, focus management, and keyboard navigation", following WAI-ARIA design patterns where possible; `asChild` for element control; per-primitive packages plus a `radix-ui` meta-package. https://www.radix-ui.com/primitives/docs/overview/introduction
  - **Base UI** — **stable; v1.0.0 shipped 2025-12-11, latest 1.8.0 on 2026-09-04**; package **renamed from `@base-ui-components/react` to `@base-ui/react`**. Unstyled; styling hooks are `data-*` attributes (`data-pressed`, `data-starting-style`) and CSS custom properties. Two documented Tailwind setup requirements: `isolation: isolate` on the layout root so portaled popups render on top, and `body { position: relative }` for iOS 26+ Safari dialog backdrops. https://base-ui.com/react/overview/releases · https://base-ui.com/react/overview/quick-start
  - **React Aria** — "style-free out of the box", 50+ components with built-in behaviour, accessibility and i18n; hooks are per-part `react-aria-*` classes, data attributes, render props, and a Tailwind plugin. https://react-spectrum.adobe.com/react-aria/index.html
  - **No primary source ranks them.** Choosing is **[opinion]**. Radix has the largest ecosystem and is already in this repo; Base UI is now stable and is MUI's successor line; React Aria has the deepest documented i18n/behaviour coverage. Pick one — each ships its own focus trap and portal, and two on one page is how focus bugs are born.
- **Dark-only**: `dark:` defaults to `prefers-color-scheme`, redefined via `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *))` for explicit control. The docs prescribe no dark-only recipe; **[opinion]** declare dark values directly in `@theme` and skip `dark:` entirely — which is what Kohlab already does. https://tailwindcss.com/docs/dark-mode
- **Browser floor is a real constraint**: Tailwind v4 needs Safari 16.4+, Chrome 111+, Firefox 128+ (it relies on `@property` and `color-mix()`) and "will not work in older browsers". https://tailwindcss.com/docs/upgrade-guide#browser-requirements

## 8. Performance

- **Core Web Vitals are LCP, INP, CLS** — all Stable, assessed at **p75**, segmented mobile/desktop. **FID is retired**; INP is its documented successor. https://web.dev/articles/vitals
- **Thresholds**: LCP good ≤ **2.5 s**, poor > **4.0 s**. INP good ≤ **200 ms** (docs: "websites should strive to have an Interaction to Next Paint of 200 milliseconds or less"), needs-improvement ≤ 500 ms, poor > **500 ms**. CLS good ≤ **0.1**, poor > **0.25**. https://web.dev/articles/lcp · https://web.dev/articles/inp · https://web.dev/articles/cls
- **INP is latency to the next paint** — input delay + processing + presentation. It observes only clicks/taps/keypresses (not scroll or hover) and ignores roughly the highest interaction per 50. Because users keep dashboards open for days, the docs say to report metrics on `visibilitychange`, not only on unload. https://web.dev/articles/inp
- **Long tasks are > 50 ms.** Yield after ~50 ms elapsed, not per item. `setTimeout(fn, 0)` is the portable yield but has a 5 ms nested-timer clamp and queues behind other work; `scheduler.yield()` resumes ahead of same-priority tasks — its support block states Chrome/Edge 129+ and Firefox 142+, with **Safari unsupported** — so use the documented enhancement `await globalThis.scheduler?.yield?.()`. `requestIdleCallback` is the documented home for low-priority work; the docs "strongly recommend" a `timeout` for required work. https://web.dev/articles/optimize-long-tasks · https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield · https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback
- **`content-visibility: auto`** skips layout+paint for off-screen content while keeping it in the DOM *and the accessibility tree*, so find-in-page and focus still work — pair it with `contain-intrinsic-size: auto 500px` so skipped content does not collapse and shift layout. Caveat: `display:none`/`visibility:hidden` elements *inside* skipped content stay exposed to the a11y tree; add `aria-hidden="true"` if that matters. `contentvisibilityautostatechange` fires when skipping starts/stops — the documented hook to pause canvas-style work. https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility · https://developer.mozilla.org/en-US/docs/Web/CSS/contain-intrinsic-size
- **Lazy-mounting heavy widgets**: `IntersectionObserver` is the documented primitive for "mount as it approaches the viewport", with `rootMargin` letting you act pre-visibility; callbacks run on the main thread and should stay cheap. https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API
  - **[opinion]** Gate both heavy widgets: Monaco mounts on IntersectionObserver + `lazy`; xterm mounts only when its tab is selected, and terminal scrollback is never rendered through React.
- **Keeping INP low with a live terminal** **[opinion, assembled from the above]**: (1) terminal WS bytes must not enter component state — xterm writes to its own buffer; (2) coalesce frames and flush on `requestAnimationFrame` rather than per message; (3) every growing list (log, file tree, transcript) gets `content-visibility: auto` + `contain-intrinsic-size`; (4) heavy parsing (diffs, large logs) goes to a Web Worker via the Vite form above; (5) stop polling and rendering work when `document.hidden`. https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API

## 9. Testing

- **Vitest 5.0.1** (5.0 announced 2026-09-03) reuses `vite.config.*`, so plugins and aliases apply to tests unchanged. Requires Vite ≥ 6.4.0 and Node ≥ 22.12. https://vitest.dev/guide/ · https://vitest.dev/blog
- **Environments**: `node` (default), `jsdom`, `happy-dom`, `edge-runtime`. Vitest's wording: happy-dom is "considered to be faster than jsdom, but lacks some API". Neither ships with Vitest. Browser tests are **not** an `environment` value — they are a separate test project. https://vitest.dev/guide/environment
- **Vitest Browser Mode**: I grepped `https://vitest.dev/guide/browser/` for `experimental`/`stable` and found **zero matches** — no status banner; it has its own config tree and a `vitest init browser` scaffolder. The precise claim is "documented as a first-class feature, not marked experimental"; a stronger "officially declared stable" is **UNVERIFIED**. Providers: `preview` (dev only) or `@vitest/browser-playwright` / `@vitest/browser-webdriverio` for CI (Playwright recommended for parallel execution). Documented limit: `vi.spyOn` on module exports throws (browser ESM namespaces are sealed) — use `vi.mock(path, { spy: true })`. Its docs **explicitly warn against `@testing-library/user-event` in Browser Mode**. https://vitest.dev/guide/browser/
- **@testing-library/react 16.3.3**, peers React `^18 || ^19`. Guiding principle, verbatim: "The more your tests resemble the way your software is used, the more confidence they can give you." https://testing-library.com/docs/guiding-principles
- **What not to test is documented, not folklore**: don't assert component instances, internal state, props, internal methods, or shallow output — "Because users can't directly interact with your app's component instances … doing those things in your tests reduce the confidence they're able to give you." Shallow rendering is deliberately unsupported. https://testing-library.com/docs/react-testing-library/faq
- **Query priority**: `getByRole` with a `name` is "your top preference for just about everything", then label/placeholder/text/display-value, then alt/title; `getByTestId` is "only recommended for cases where you can't match by role or text … (e.g. the text is dynamic)". `findBy*` = `getBy*` + `waitFor` (defaults 50 ms interval, 1000 ms timeout), and `waitFor` retries only when the callback **throws** — a falsy return does not retry. Prefer `findBy*` over `waitFor` + `getBy*`. https://testing-library.com/docs/queries/about · https://testing-library.com/docs/dom-testing-library/api-async
- **`user-event` over `fireEvent`**: "`fireEvent` dispatches *DOM events*, whereas `user-event` simulates full *interactions*", including visibility/interactability checks. Use `userEvent.setup()`. https://testing-library.com/docs/user-event/intro
- `@testing-library/jest-dom@7.0.1` ships a first-class `@testing-library/jest-dom/vitest` entry. https://testing-library.com/docs/ecosystem-jest-dom/
- **Fake timers** (`vi.useFakeTimers`): `process.nextTick` mocking is unsupported under `--pool=forks`; `toFake`/`toNotFake` are mutually exclusive; `runAllTimers` throws after 10 000 iterations on infinite intervals. `vi.waitFor` auto-advances timers when fakes are on. https://vitest.dev/api/vi
- **`eslint-plugin-testing-library` encodes the anti-patterns**; the ones that catch real bugs: `await-async-queries`, `await-async-utils`, `no-wait-for-side-effects`, `no-wait-for-multiple-assertions`, `no-node-access`, `no-container`, `no-unnecessary-act`, `prefer-presence-queries`, `prefer-user-event`. https://github.com/testing-library/eslint-plugin-testing-library
- **[opinion] Test**: pure logic with real branches (status derivation, diff/log parsing, WS message decoding, store reducers); the optimistic/rollback path; error-boundary behaviour (a throwing child renders the fallback). **Don't test**: that `refresh()` was called, that a prop was forwarded, snapshots of class strings, or anything needing a real socket — the RTL FAQ already forbids the first three; for the last, prefer a hand-rolled fake over globally mocking `WebSocket`.

## Implications for Kohlab

1. **[MUST]** Upgrade `react`/`react-dom` to 19.3.x with `@types/react*` in lockstep; adopt no hook from §1 while on 18.3.
2. **[MUST]** Add a root error boundary, per-panel boundaries (terminal, log, diff, file tree), and one around every `lazy`+`Suspense` region — a failed chunk throws into the nearest boundary.
3. **[MUST]** Pass `onUncaughtError` and `onCaughtError` to `createRoot` so render failures are observable in production instead of only in the console.
4. **[MUST]** Gate every polling loop on `document.visibilityState` and resume on `visibilitychange`; browsers throttle timers in hidden tabs but exempt WebSockets, so gate polling, not the socket.
5. **[MUST]** Keep terminal/WS bytes out of React state — write to the xterm buffer directly and coalesce frames onto `requestAnimationFrame`; the terminal must not re-render per message.
6. **[MUST]** Render every unbounded list (log, file tree, transcript) with `content-visibility: auto` paired with `contain-intrinsic-size: auto <length>`; never ship bare `auto` without the intrinsic size.
7. **[SHOULD]** Replace the fixed 3 s reconnect in `App.tsx` with the exponential backoff + cap already used in `TerminalView.tsx`, and add jitter.
8. **[SHOULD]** Make the terminal pane lazy (`lazy(() => import('./TerminalView'))`) so xterm is not fetched on first paint; chunking alone does not defer a static import.
9. **[SHOULD]** Move workspace actions to `useOptimistic` + `startTransition` instead of await-then-`refresh()`, and let the reducer form — not manual patching — reconcile optimistic entries against a snapshot that changes mid-flight.
10. **[SHOULD]** Add `class-variance-authority`, wrapped by the existing `cn()` helper, and keep every variant class string fully static — Tailwind cannot see interpolated class names.
11. **[SHOULD]** Choose exactly one primitive library (Radix, Base UI, or React Aria) for all dialogs/popovers/menus; do not run two, because each brings its own focus trap and portal.
12. **[SHOULD]** Stand up Vitest + RTL + `jest-dom/vitest` + `user-event` with `eslint-plugin-testing-library`, and test only behaviour observable through the DOM — never internal state, component instances, or call wiring.
13. **[SHOULD]** Migrate the Vite config off deprecated `rollupOptions.manualChunks` when moving to Vite 8, and delete the dead `lucide-react` chunk entry.
14. **[MAY]** Adopt TanStack Query when a second independently-invalidated resource exists; until then a hand-rolled deduped, visibility-gated fetch layer meets React's stated requirements with less surface area.
15. **[MAY]** Enable React Compiler only after `eslint-plugin-react-hooks@7` is clean, pinned exactly (`--save-exact`) and backed by e2e coverage; do not strip existing `useMemo`/`useCallback` until the app has been tested under the compiler.
